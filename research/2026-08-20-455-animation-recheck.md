# #455 — Animation Re-check Against Today's Catalogue

## The Question

`research/766-animated-dataviz-findings.md` concluded: build three animated forms — (1) metric-to-metric transition, (2) small multiples, (3) slope chart — and explicitly do not build animated map fills. That was written against a smaller and partly-assumed metric catalogue. Does the conclusion still hold against the catalogue as it exists on 2026-08-20?

Answered below with counts, not opinion.

## Headline Answer

**766 holds on 2 of its 3 builds and holds completely on its negative recommendation. Item 3 (slope chart) is dead and must be struck.**

The catalogue contains **zero** metrics with two or more comparable time points. Not "few" — zero. Every one of the 124 metrics is a single cross-section. This kills the slope chart outright, and it strengthens rather than weakens the case for the two forms that need no time axis.

## Method

All queries run read-only against `/mnt/storage/websites/mapsofbharat/data/mapsofbharat.db` via `sqlite3`. Every number below is reproducible from the SQL given.

### Catalogue size

```sql
SELECT COUNT(*) FROM metrics;                                          -- 124
SELECT COUNT(*) FROM metric_values;                                    -- 71552
SELECT COUNT(DISTINCT region_code) FROM metric_values
  WHERE region_level='district';                                       -- 735
```

### Q1 — Metrics with two or more time points

Step 1, the naive count — how many metrics have rows in more than one `year`:

```sql
SELECT n_years, COUNT(*) AS n_metrics FROM (
  SELECT metric_id, COUNT(DISTINCT year) AS n_years
  FROM metric_values GROUP BY metric_id
) GROUP BY n_years ORDER BY n_years;
```

| n_years | n_metrics |
|---|---|
| 1 | 119 |
| 3 | 5 |

That naive count says "5 metrics have 3 years". It is misleading, and the next step is the one that matters.

Step 2, the decisive test — a time point only exists if **the same region** is observed in **two different years**:

```sql
SELECT COUNT(*) AS n_pairs FROM (
  SELECT metric_id, region_code, region_level, COUNT(DISTINCT year) AS ny
  FROM metric_values
  GROUP BY metric_id, region_code, region_level
  HAVING ny >= 2
);
```

Result: **0**.

Not one (metric, region) pair in the entire database is observed in two years. The `year` column on those 5 metrics is a **per-state vintage stamp**, not a time axis:

```sql
SELECT metric_id, year, COUNT(*) AS n_regions
FROM metric_values
WHERE metric_id IN ('econ_percapita_nsdp_rbi','fiscal_deficit_pct_gsdp','gsdp_growth',
                    'outstanding_debt_pct_gsdp','own_tax_pct_gsdp')
GROUP BY metric_id, year ORDER BY metric_id, year;
```

| metric_id | 2022 | 2023 | 2024 | total states | total rows |
|---|---|---|---|---|---|
| econ_percapita_nsdp_rbi | 1 | 8 | 25 | 34 | 34 |
| fiscal_deficit_pct_gsdp | 1 | 5 | 25 | 31 | 31 |
| gsdp_growth | 1 | 8 | 25 | 34 | 34 |
| outstanding_debt_pct_gsdp | 1 | 5 | 25 | 31 | 31 |
| own_tax_pct_gsdp | 1 | 5 | 25 | 31 | 31 |

Rows equal states in every case. Each state appears exactly once, tagged with whichever fiscal year *that state's* latest RBI figure was published for. `metrics.methodology` confirms this in the source's own words:

- `econ_percapita_nsdp_rbi`: *"per state its latest published fiscal year (2024-25 where available, else 2023-24)"*
- `fiscal_deficit_pct_gsdp`: *"Latest common FY per state: 2024-25 is Budget Estimates (BE), 2023-24 Revised Estimates (RE), 2022-23 Actuals (A)"*

These are worse than merely non-comparable across years — the mixed BE/RE/Actuals basis means even the single cross-section blends three different estimate vintages. `metrics.year` is 2024 for all five, i.e. the catalogue itself already treats them as one 2024 cross-section.

Step 3, corroboration from the ingest log — no adapter has ever loaded a second year:

```sql
SELECT adapter, COUNT(DISTINCT year) AS ny FROM load_log
GROUP BY adapter HAVING ny > 1;
```

Result: **zero rows**. Every one of the ~35 ingest adapters is single-vintage.

Step 4, ruling out a hidden second point in the 2011-vintage levels. Twelve metrics carry `district2011`/`state2011` rows alongside `district`/`state`:

```sql
SELECT metric_id, region_level, year, COUNT(*) FROM metric_values
WHERE metric_id IN (SELECT DISTINCT metric_id FROM metric_values WHERE region_level='district2011')
GROUP BY metric_id, region_level, year;
```

All four levels carry `year = 2011` for all twelve metrics (630 vs 733 districts, 35 vs 36 states). This is the *same* Census 2011 data rendered on historical vs current boundaries — a geometry variant, not a time point.

Step 5, the specific carriers 766 named for slope charts:

```sql
SELECT id, name, year, source FROM metrics
WHERE id IN ('voter_turnout_ls2024','vehicles_per_1000','agri_rice_production',
             'agri_wheat_production','agri_cropped_area','rain_annual_mm');
```

| Metric 766 assumed had 2 points | Years actually held |
|---|---|
| `voter_turnout_ls2024` (766: "2009 vs latest") | 2024 only |
| `vehicles_per_1000` (766: "2001 vs latest") | 2015 only |
| APY crops — `agri_rice_production` etc. (766: "1997 vs 2014") | 2014 only |
| `rain_annual_mm` (766: "rainfall decadal") | 2024 only |

Every carrier 766 named is single-vintage. 766's "Holdings: partial" for the slope chart was optimistic; the correct value is "Holdings: none".

### Q2 — Families sharing one unit and scale

Naive grouping by `unit` alone:

```sql
SELECT unit, COUNT(*) AS n_metrics, COUNT(DISTINCT category) AS n_cats
FROM metrics GROUP BY unit ORDER BY n_metrics DESC;
```

75 of 124 metrics share the unit `%`, spread over 16 categories. That number alone overstates the case: a family can only share a small-multiples grid if its members also share a **geometry** (the same district set) and a **vintage** (so the panels are one snapshot, not a collage). The operative grouping is therefore *source cohort + unit + level*.

```sql
SELECT substr(m.source,1,45) AS src, m.unit, COUNT(DISTINCT m.id) AS n
FROM metrics m
JOIN metric_values v ON v.metric_id = m.id AND v.region_level = 'district'
GROUP BY m.source, m.unit HAVING n >= 3 ORDER BY n DESC;
```

and, per family, the districts on which *every* member has a value:

```sql
WITH fam AS (SELECT id FROM metrics WHERE source LIKE '%<pattern>%' AND unit = '<unit>')
SELECT (SELECT COUNT(*) FROM fam) AS family_size, COUNT(*) AS shared_districts
FROM (
  SELECT region_code FROM metric_values
  WHERE region_level='district' AND metric_id IN (SELECT id FROM fam)
  GROUP BY region_code
  HAVING COUNT(DISTINCT metric_id) = (SELECT COUNT(*) FROM fam)
);
```

## Per-Form Verdict

### 1. Animated metric-to-metric transition — BUILD. Unblocked.

**Buildable now.** This form's defining property is that it needs **zero** time points: it animates a re-sort between two *different metrics* on the same geography. The finding that killed the slope chart does not touch it.

The pool is larger than 766 assumed: 72 district-level metrics with >=690 district coverage, sharing 576 districts on which all 72 have a value — that is 72 x 71 = 5,112 ordered district-level pairs, plus 82 x 81 = 6,642 state-level pairs. 28 metrics have complete 733-district coverage for the cleanest pairs.

The only cost is engineering, and it is real but small: `package.json` currently carries `maplibre-gl` and `d3-scale-chromatic` only — no D3 core, no Observable Plot, no Framer Motion. 766's stack recommendation (D3 + SVG, ~1s staged transitions per Heer & Robertson 2007, 735 nodes inside the ~3,000-node smooth zone) requires adding D3 selection/transition/scale modules. That is a dependency decision, not a blocker.

**Blocker: none.**

### 2. Small multiples — BUILD. Unblocked, and stronger than 766 assumed.

**Buildable now, in indicator mode.** 766 scoped this correctly as "entire catalogue (indicator-mode); vehicle stock/turnout/APY/rainfall (sparse-time)". The sparse-time half of that sentence is now void — there is no time mode for anything. The indicator-mode half is not merely intact but better evidenced than 766 could show: 8 concrete families, 58 metrics, with named shared-district counts.

Three families (religion, worker category, household assets) are part-to-whole decompositions on the complete 733-district set, which is the ideal small-multiples case and was not identified in 766.

Two families need free per-panel axes rather than one shared axis (NCRB crime spans 0-2168 vs 0-14; religion spans 0-99.4 vs 0-4.1). That is a normal small-multiples design choice, not a blocker — but it must be a deliberate decision at build time, not a default, because a shared linear axis would render 5 of 6 religion panels and 3 of 4 crime panels as flat lines.

**Blocker: none.**

### 3. Slope chart — DO NOT BUILD. Blocked, permanently, by data.

**Blocked.** A slope chart requires exactly two comparable observations per entity. The catalogue contains **zero** metrics with two comparable observations of any entity. Not a threshold problem — a zero problem. There is no value of N below a threshold here; N is 0.

Every carrier 766 named has been checked individually and is single-vintage (voter turnout 2024 only, vehicle stock 2015 only, APY 2014 only, rainfall 2024 only). 766's own caveat — *"whether a 2001 Census point is held is also unconfirmed"* — resolves to: it is not held, and neither is any other second point.

This is not fixable by engineering. It is fixable only by ingesting a second vintage of some series (Census 2001 PCA, LS 2019 turnout, an earlier APY year, or a multi-year IMD rainfall pull), which is a data-pipeline project, not a dataviz project.

One tempting escape hatch, closed for the record: a slope chart *can* be drawn between two different metrics (rank on metric A -> rank on metric B). But that is exactly form #1 rendered as two parallel axes instead of an animated re-sort. It adds no information form #1 lacks, and shipping both would be two UIs for one idea. If a static companion to form #1 is wanted, draw it as form #1's `prefers-reduced-motion` fallback, not as a third product.

**Blocker: 0 of 124 metrics have a second comparable time point; 0 of ~35 ingest adapters have ever loaded a second year.**

## Sanity Check: "Do Not Animate Map Fills"

**Confirmed, and the reasoning is now stronger than 766's.**

766 rested this on evidence: Fish, Goldsberry & Battersby (2011) on change blindness in animated choropleths, and Tversky, Morrison & Betrancourt (2002) on animation rarely beating static graphics. That evidence still stands and nothing in this recheck contradicts it.

But the recheck supplies a prior and simpler reason. An animated map fill animates a choropleth **across time**. With 0 metrics holding 2+ comparable time points, a time-animated fill has exactly one frame. There is nothing to animate. The recommendation moves from "the evidence says avoid this" to "this is arithmetically impossible", which is a firmer footing.

One clarification worth recording so a future reader does not mistake it for a contradiction: form #1 (metric-to-metric transition) *does* re-colour polygons, and if rendered on the map rather than as a beeswarm it would technically be an animated map fill. That is a different thing from what 766 rejected. 766 rejected the **time-slider choropleth** — animating one metric across years. Animating *between two metrics* at a fixed instant is legitimate, carries no change-blindness liability of the year-to-year kind (the reader is told the metric changed, and the legend changes with it), and is precisely the form the evidence supports. The rule to record is: **never animate a fill across time; animating a fill across metrics is fine.**

## Recommendation

**Strike item 3 from 766's Recommended Plan. Keep items 1 and 2. Keep the entire "Not Doing" list, and add the slope chart to it.**

Revised plan:

1. **Small-multiple indicator grid** — BUILD FIRST. Cheapest, best-evidenced (Robertson et al. 2008; Brehmer et al. 2019 for mobile), and now has 8 named families and 58 metrics behind it. Seed it with the three part-to-whole families on the complete 733-district set (religion 6, household assets 5, worker category 4) — they are the clearest reads and need no axis compromise. Design decision required at build time: per-panel free axes for the crime and religion families.

2. **Animated metric-to-metric transition** — BUILD SECOND. 72-metric district pool on 576 fully shared districts; 82-metric state pool. Requires adding D3 core modules to a `package.json` that currently has only `d3-scale-chromatic`. Ship with the `prefers-reduced-motion` instant-swap fallback and `aria-live` announcement that 766 Q5 already specifies.

3. **Slope chart** — DO NOT BUILD. Recorded "no", with the number that justifies it: **0 of 124 metrics have two comparable time points**. Revisit only if and when a second vintage of some series is ingested; until a `load_log` row exists showing an adapter loading a second year for an existing metric, this stays closed.

4. **Animated map fills across time** — DO NOT BUILD. Recorded "no": **0 metrics with 2+ time points means 1 frame**. Unchanged from 766.

Also void, as consequences of the same zero: 766's "Q7 minimum credible version" builder (its stated carriers — vehicle stock, turnout, APY, rainfall — all have one point each, so a bar-race or line-race template has nothing to race), and the connected scatterplot and horizon chart, which 766 already listed as blocked and which are now blocked for the additional and simpler reason that their time axis does not exist.

The one-line summary for the tracker: **766's conclusion holds for the two forms that need no time axis and is void for the one that does; build small multiples and the metric-to-metric transition, do not build the slope chart, and do not animate map fills across time.**
